## PH09b-025 — Seven published JSON payloads carry a build date, so every rebuild produces a spurious diff

**Severity:** Medium · **Category:** Tooling / generation · **CERTAIN**

**Evidence.** The entire drift, in full:

```diff
- "generated": "2026-08-08",
+ "generated": "2026-08-09",
```

Seven files: the six `flashcards/data/*.json` deck payloads and
`past-paper-questions/questions.json`. Nothing else in the repo moved.

**Nothing consumes the field.** `grep -rn 'generated' js/components/*.js` returns
two hits, both inside comments — `flashcards.js:3` and `question-search.js:4`.
No runtime code reads it.

**Why it matters.** It is small and it is the exact defect the sitemap generator
was already fixed for. `be3ec19` records that "two generators stamp build dates
into `sitemap.xml`", and `build_sitemap.py`'s own docstring explains the harm:
440 of 461 entries carried one of three build dates, so "a page untouched since
May was advertised as modified today and Google had no reason to trust the
field." The sitemap was fixed to take `lastmod` from git. **The JSON payloads
were not.**

The consequence is narrower than the sitemap case but real: **you cannot tell
"my source changed" from "I re-ran the build".** Every rebuild dirties seven
files, so the honest habit — re-run the generators, check `git diff` is empty,
commit only real changes — does not work. Over time that trains you to `git add`
generated output without reading the diff, which is how a hand-edit to a
generated file gets committed unnoticed. That has not happened yet; this is the
mechanism by which it would.

It also makes CLAUDE.md's "generating twice is byte-identical" claim true of the
HTML and false of the JSON, without saying so.

**Recommendation.** P10. Pick one:

- **Drop the field.** Nothing reads it. Simplest, and makes rebuilds a true
  no-op.
- **Take it from git**, exactly as `build_sitemap.py` does — the newest commit
  date across the generator's inputs. Keeps a meaningful "data as of" for anyone
  reading the JSON, and only changes when the data does.

I would drop it: `build_sitemap.py` already publishes accurate freshness in the
place crawlers actually read, and a second, differently-derived date in a payload
nobody reads is a thing to keep correct for no return.

**Effort:** S · **Risk of acting:** Low — one line per generator, and the next
rebuild proves it ·**Risk of not acting:** Low-Medium, and it is the mechanism
behind a worse failure rather than the failure itself · **Dependencies:** none ·
**Status:** OPEN

## PH09b-026 — `--check` does not check the output, only the input

**Severity:** Medium · **Category:** Tooling / governance · **CERTAIN**

**Evidence.** Five generators expose `--check`, documented as "validate, write
nothing". Four of them do exactly that and no more — they validate the source
data, render into memory and discard it. Only `build_sitemap.py` compares what it
would write against what is committed:

```python
# scripts/build_sitemap.py:252
if not p.exists() or p.read_text(encoding="utf-8") != body]
    print(f"  WOULD CHANGE {p.relative_to(ROOT)}")
```

Searching the other four for any comparison against existing output —
`WOULD CHANGE`, `read_text() !=`, `filecmp` — returns **0 hits in each**.

So all four report success on stale output:

```
build_past_paper_taxonomy --check   →  "check only - nothing written"   exit 0
build_glossary            --check   →  "--check: nothing written"       exit 0
build_past_paper_questions --check  →  "check only - nothing written"   exit 0
build_questions           --check   →  "OK - 166 set(s) ... nothing written"  exit 0
```

Every one passed. And yet running them for real changed seven files. **`--check`
passing does not mean the committed output is current** — it means the inputs
parse.

**Why it matters.** This is the same shape as PH00-011, where `verify_liquid.py`
guards against a deploy-killing bug but fires on a false positive. Here the check
is the opposite failure: a **false negative**. It is the natural thing to run
before committing, its name implies it verifies the build, and it cannot detect
the one condition that matters — that generated output has drifted from its
source. PH01-017 is a worked example: the sitemap had four stale `lastmod` values
and only `build_sitemap.py`'s stronger `--check` caught it.

**Recommendation.** P10. Give the other four the comparison
`build_sitemap.py` already has: render, compare to the file on disk, print
`WOULD CHANGE <path>`, exit non-zero if anything differs. It is a small,
copyable pattern and it turns `--check` into a pre-commit hook worth having.

Fix PH09b-025 first, or all five will report drift on every run and the check
will be ignored — which is the PH00-011 failure mode again.

**Effort:** S-M · **Risk of acting:** Low · **Risk of not acting:** Medium — the
repo's only drift detector covers one generator of six · **Dependencies:**
PH09b-025 should land first · **Status:** OPEN

## Generation coverage

| Generator | Pages | Share |
| --- | ---: | ---: |
| `build_questions.py` | 173 | 37% |
| `build_past_paper_questions.py` | 90 | 19% |
| `build_flashcards.py` | 7 | 2% |
| `build_glossary.py` | 3 | 1% |
| **Generated** | **273** | **59%** |
| **Hand-written** | **190** | **41%** |

The hand-written 190:

```
 166  revision-notes topic pages  (6 board directories)
   9  root: index, tutoring, marking, about, contact, faq, privacy,
        confirmation, 404
   6  revision-notes hubs + 2 diagram galleries + macro-application + index
   5  past-papers hubs
   4  (remainder of the above groupings)
```

**This is the number P6 turns on.** The 273 generated pages already have a
template layer — changing every `<head>` in `practice-questions/` is one edit to
`build_questions.py` and a rebuild. The 190 hand-written pages have none, and 166
of them are the revision notes, which are the pages the owner says are finished.

So PH00-004 ("463 hand-maintained `<head>` blocks") is **overstated and should be
read as 190**, of which 176 are notes and hubs. That is a materially smaller and
more tractable problem than the Phase 0 framing suggested, and P6 should be
scoped to it rather than to all 463.

One consequence worth stating for P6: a template layer covering the hand-written
190 would have to **coexist** with four Python generators that emit their own
`<head>`, or absorb them. Coexistence means the same `<head>` defined twice, in
two languages. That tension is P6's central design question, and it is now
quantified.
